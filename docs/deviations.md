# 实现与需求文档的口径差异

需求文档 `数据库实践-需求.html` 是课程给的需求规格，实现按 `PLAN.md` 的口径走。凡是两者字面不一致的地方都登记在这里，答辩时按这张表回答，不要临场解释。

## 1. 退票后订单状态：需求写"订单变为已退票"，实现是"整单退干净才变"

- 需求（`数据库实践-需求.html` 模块三·退票处理）："系统自动计算退款金额，订单状态变为"已退票"，座位释放"。
- 实现：`ticket.status` 逐张变 `已退票`；`orders` 只有在**这张单再没有 `已支付`/`已检票` 的票**时才变 `已退票`，否则保持 `已支付`，`orders.total_amount` 递减已退现金。
- 理由：一张订单可以含 1–5 张票（模块三·选座："选择座位（可多选，最多 5 张）"），退其中一张就把整单标成"已退票"会让剩下没退的票失去归属状态。票级状态才是真相，订单只是汇总（`PLAN.md` §1.1、`GLOSSARY.md`「部分退票」）。
- 对需求字面的覆盖：整单全部退掉时，行为与需求完全一致。
- 注意：判据是**有效票计数**，不是 `total_amount` 归零。2 小时内退票扣 20% 手续费且手续费不退，金额永远归不了零。

## 2. 改签窗口：需求写"发船前 1 小时以上"，实现要求原班次和目标班次都满足

- 需求（模块三·改签规则）："仅"已支付且未检票"的订单可改签；发船前 1 小时以上可改签；需补差价（新班次贵则补差价，便宜则退差价）"。
- 实现：原班次 `depart_time > now + 1h` **且**目标班次 `depart_time > now + 1h`，两条都满足才允许（两个不同的 409 文案）；满足时**允许改到更早的班次**。
- 理由：需求只约束了原班次。若目标班次可以是马上就要开的船，乘客会在开船前几分钟把票挪上去，检票口没法处理；只约束目标班次则会让"票所属班次已过发船时间"的票还能改走。

## 3. 手续费基准班次：需求没写，实现按票所属班次

- 需求（模块三·退票处理三档）：按"距发船时间"分档，没说按哪个班次。
- 实现：按 `ticket.schedule_id` 指向的班次（即票所属班次）的 `depart_time` 实时比 `now`；改签过的票按新班次算，不是按订单初次下单的班次（订单的 `schedule_id` 永远停在初次下单那一班）。
- 理由：改签后乘客确实是坐新班次的船，手续费按新班次才说得通（`PLAN.md` §1 口径段）。

## 4. 一人一票的判重键：需求没写，实现用身份证号

- 需求（模块三·选座）："每张票需填写乘客姓名+身份证号+手机号"；模块三未说明"一人一票"按什么判重。
- 实现：同一班次内按 `ticket.id_card` 判重，状态只算 `已支付`/`已检票`（已退票、已取消不算）。不按账号判重。
- 理由：账号只代表"谁在买"，帮家人买或售票员代买时，同账号要为不同人买票；按账号判重会让代买功能直接失效。

## 5. M3 范围内没有的东西

以下需求点在别的里程碑实现，不算本 PR 的缺陷：

- 班次状态流转（待发布 → 售票中 → 已发船 → 已完成）：没有定时任务把过期班次推进到"已发船"，M3 只按 `depart_time` 与 `now` 做时间兜底（退票/改签窗口都实时比时间），班次状态留在 M2/后台补。
- 检票（模块四）：`check_in` 表与触发器已在 `database.sql` 里，接口与界面在 M4。
- 统计报表（模块五）：`v_seller_performance` 视图已在库里，报表页在 M5。

## 6. 验收时顺带修掉的前端缺陷：响应拦截器把 `data` 提前拆掉

- 现象：乘客端「我的船票」、售票员端「代售订单」打开后一直显示「暂无订单」，真实浏览器点验才暴露；接口本身 200 且有数据，是前端没显示出来。
- 原因：`frontend/src/api/request.js` 的响应拦截器按 `{success,message,data}` 把 `body.data` 拆出来返回，但全部页面（订单列表、班次查询、选座、改签弹窗）都是按 `res.data` 取业务数据的。两边约定不一致，列表拿到 `undefined` → 显示「暂无订单」。
- 处理：拦截器只判断成功与否，**原样把整个响应体交回去**，页面按 `res.data` 取数；只有 `store/user.js` 两处取 `authApi.current()/login()` 的地方改成 `.data`，并补了 2 个拦截器回归用例（`frontend/src/api/request.test.js`）。
- 关联：这条不是需求口径问题，是 M3 退改签界面可用的必要前置，登记在此以免被当成漏改。
