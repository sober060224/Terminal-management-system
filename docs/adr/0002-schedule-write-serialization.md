# 0002 一个班次的所有写操作都拿同一把悲观锁

下单、支付、退票、改签、检票、取消班次、超时释放——七个入口全部在事务第一句执行 `SELECT ... FROM schedule WHERE id = ? FOR UPDATE`，再动 `seat` / `orders` / `ticket`。锁顺序固定为 schedule → seat → orders → ticket，只有一个 `ScheduleLock.lock(scheduleId)` 入口，不分散写。理由：一条 SQL 就正确，50 线程抢同一座位的演示脚本能现场跑出"1 个成功、49 个 409"；需求 3.4 允许"事务方案"，乐观锁要处理重试，课程项目里是纯负担。锁粒度粗到班次，被牺牲的是同班次不同座位的并行度，300 座的小船无所谓。

## Status

已采纳。

## Considered Options

- 乐观锁（`version` 列 + 重试）：并发正确性依赖重试次数，演示时会出现"偶发失败"，答辩解释成本高。
- 只锁被选的座位行：两个乘客同时买不同座位时仍可能交叉更新 `sold_seats` 计数器，且退票 + 支付会争同一班次的两个不同行，锁顺序容易写错。

## Consequences

同一班次上的操作串行；压测 QPS 上限就是锁的吞吐，但演示场景只有几十个并发。所有涉及班次的写代码必须记住先 `ScheduleLock.lock`，漏一处就有幽灵并发。
