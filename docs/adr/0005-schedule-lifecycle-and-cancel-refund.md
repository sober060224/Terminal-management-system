# ADR-0005：班次生命周期与取消退票的实施口径

- 状态：已采纳（模块二，2026-11-25）
- 相关：ADR-0002（悲观锁与锁顺序）、ADR-0003（座位状态惰性判断）、`PLAN.md` D7、`docs/deviations.md` §15–§18

## 背景

需求模块二要求管理员维护航线、船舶、班次，并给出两条带有副作用的规则：

1. 班次状态要按 `待发布 → 售票中 → 已发船 → 已完成` 流转，`售票中` 还能被管理员取消；
2. 取消班次时"已购票乘客收到系统通知，支持全额自动退票"。

这三处都有多种做法，选错了后期很难改：状态推进放在读侧还是写侧、取消退票复用哪条退票通路、
换船时座位怎么重建。本 ADR 把口径定死。

## 决定

### 1. 状态推进：手动发布 + 定时任务 + 读侧兜底，三层并存

- `待发布 → 售票中`：**只有管理员手动发布**（`POST /api/admin/schedules/{id}/publish`）。
  新班次一律以 `待发布` 落库，避免"填完就开卖"。
- `售票中 → 已发船 → 已完成`：由 `ScheduleStatusJob`（`fixedDelay = PT1M`）用**条件更新**
  推进（`where status = '售票中' and depart_time <= now`）。条件更新保证并发下只有一方能改到行，
  且状态不会回退。
- **读侧过滤保留**：下单、改签、班次列表仍按 `depart_time` / `arrive_time` 实时判定，
  不信任 `status` 字段是否已推进。定时任务没跑（机器刚重启、任务被关）时业务仍然正确。

理由：把状态当成"缓存"而不是"真相来源"。若业务正确性依赖定时任务准点，一次任务失败就会
放出已发船的票；反过来，只靠读侧过滤则管理端界面永远显示"售票中"，管理员没法看到真实进度。

### 2. 取消退票：独立通路，复用锁顺序，不复用公开退票接口

- 取消班次的全额退票**不走** `POST /api/tickets/{id}/refund`：那个接口按三档手续费算钱，
  且退票原因走白名单（`行程变更/重复购票/误购/其他`），营业口径上不该允许乘客拿"班次取消"退款。
- 新增内部通路 `AdminScheduleService.cancel`：`refund_amount = ticket.price`（全额、零手续费）、
  `refund_reason = '班次取消'`（不在白名单里，只能由系统写入）。
- 锁顺序与 ADR-0002 完全一致：**schedule → orders → ticket → seat**。先锁班次行，
  整条链路串行，下单/退票/改签撞上取消时会被挡在班次锁外面，随后看到 `已取消` 状态而拒绝。

理由：手续费规则是"乘客单方面退票"的补偿条款，班次被取消是运营方违约，不该扣钱。
把它做成独立通路，白名单和费率都不用为特例开口子。

### 3. 换船：重建座位，但只允许在"零售票记录"时换

- 新建班次的座位只由数据库触发器 `trg_schedule_generate_seats` 生成，Java 不复刻。
- 编辑班次换船时，若座位数不同，删旧座位 + 用 `SeatGenerator` 重建（规则与触发器逐字一致，
  由单测锁定）。
- **限制**：该班次有任何 `ticket` 记录（含已退票/已取消）就不许换船。原因：`ticket.seat_id`
  是外键，删座位会破坏历史票；且换到小船可能装不下已售出的座位。

理由：换船本质上等于"换一个班次"，只有还没开始卖票时才是纯数据修正。超过这个界限就该
取消后重建，而不是让历史票指向不存在的座位。

### 4. 区间重叠校验在应用层，不指望数据库

- `uk_ship_depart (ship_id, depart_time)` 只能拦"同船完全同一时刻"；
  "08:00–10:00 与 09:00–11:00" 这种真正会撞的冲突它拦不住。
- 应用层用 `NOT (arrive <= :depart OR depart >= :arrive)` 判定两个半开区间有交集，
  新增与编辑都过这一关；批量生成逐日判定，冲突日跳过并回报原因。

理由：见 `PLAN.md` §6。MySQL 8 没有区间排他约束（PostgreSQL 的 `EXCLUDE USING gist` 才有）；
在答辩里这反而是个能讲清楚的加分点。

## 后果

- 管理端能显示真实班次状态，且状态滞后不会造成超卖。
- 取消班次是一条可重放的事务路径，验收脚本能断言全额退款与座位释放。
- 座位号生成有两份实现（SQL 触发器 + Java），靠单测与真实库核对来防漂移（deviations §18）。
- 换船的限制会让"班次卖出几张票后想换大船"变成不可操作，需要取消重建——
  这是有意的约束，不是缺陷。
